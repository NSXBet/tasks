# Plan 02-01: Lazy changeset derivation

Phase 2 · Changeset Derivation & Completion Contract · CHG-01 (tracer slice: adapter → surface op → tk show, end to end)

## Context

Phase 1 pinned `metadata["changeset"].base` at `tk work` (01-02) and delivered the typed adapter (`packages/git`: `runner.ts`, `commands.ts`, `porcelain.ts`, all enumerated, porcelain 1:1, empty → `[]`). Phase 2 makes the PR record real: commits and changed files derive live from `issue.branch` vs the pinned base on every read (D-01), as a structured payload `commits[{sha, subject}]`, `files[{path, status}]`, `counts{additions, deletions}` (D-02), and `tk show` renders both (CONTEXT domain item 1; ROADMAP criterion 1).

Design contract: `.agents/plans/2026-10-08-task-to-review.md` §3 (derivation commands) and §product (show shape). Domain purity: no I/O in `packages/domain`; surface owns git calls; CLI parses/serializes only (`.planning/codebase/ARCHITECTURE.md`). Presentation analog: `formatShow` in `packages/cli/src/presentation.ts` (lines 210–232) already renders branch/worktree/base sections with the colored-header + aligned-lines body style — COMMITS and FILES join those.

**Locked-decision note (D-01 × D-02 reconciliation, planner-resolved):** D-01 names "the plan's two commands" (log + numstat diff). D-02 locks `files[{path, status}]`. `git diff --numstat` cannot emit status, and numstat/name-status are mutually exclusive git formats (verified empirically: a combined invocation prints only name-status). D-02's payload is therefore unreachable with exactly two commands. Resolution: derivation enumerates **three** adapter commands — `git log --oneline <base>..<branch>` (commits, D-01 literal), `git diff --numstat <base>...<branch>` (aggregate counts, D-01 literal), and `git diff --name-status <base>...<branch>` (files with status, D-02's locked shape). D-01's guarantees — adapter-enumerated, live on every read, no caching, pinned base — are preserved in full; only the command count grows. Cite this note in the derivation op's doc comment.

       - `parseNameStatus`: rows are `<code>\t<path>` or `<code>\t<old>\t<new>` for R/C; `status` is the full code token verbatim (`A`, `M`, `D`, `T`, `U`, `R100`, `C75`, …); `path` is the LAST token (destination) for two-path forms; one record per entry.
