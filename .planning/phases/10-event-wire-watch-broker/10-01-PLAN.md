Decision IDs: 10-CONTEXT.md lists its decisions unnumbered. Phase 10 plans number them in document order:
- **D-01**: No daemon. One append-only `events.jsonl` per workspace is the wire. Every mutation that matters appends one event line: status changes, `task.comment` transitions, `comments.send` batches, approvals (status → approved/rejected), and finish.
- **D-02**: `tk watch <id…>` reads the log with per-subscriber cursors and supports `--until <event>`, `--drain` and `--follow`. Many agents and clients watch at once, each with its own cursor.
- **D-03**: TUI and web live views and notifications read the same log. Web `/events` SSE tails it, and the TUI tails it. There is one stream and no second mechanism.
- **D-04**: The pi/omp extension tails the log and surfaces comments, approvals and sent review batches to the agent automatically.
- **D-05**: The superseded daemon-broker plans are reference only.

Deferred: `tk next` (no Phase 10 plan implements it).

**As an** agent or reviewer, **I want** every change to a task to be written once to an append-only event log at the
moment it is made, **so that** every surface and every agent can follow the same stream without a daemon and
without re-diffing the board.

This plan builds the write side of D-01: the log file, the envelope, event derivation, and emission on every write
path. The read side (`tk watch`, consumers) follows in 10-02..10-06. Requirements: WIRE-01 (substrate) and WIRE-03
(comments, approvals and sent batches carried on the events).

Design (spec §10 "The script and the wire", docs/html/data/task-to-review-data.js `loop.wire`):
- Log file: `<root>/.tasks/events.jsonl`. One JSON line per event: `{ "seq": 412, "host": "<os.hostname()>", "ts": "<ISO>",
  "task": "<issue id>", "type": "task.status", "actor": "<store actor>", "session"?: "<TK_SESSION>", "data": {…} }`.
- Emitted types: `task.created`, `task.status`, `task.owner`, `task.comment`, `task.update`, `task.evidence`,
  `task.worktree`, `task.deleted` (needed for board removal, not in the spec list) and `run.changed` (existing runtime-inbox
  kind, emitted from `saveRun`). `task.commit` and `task.report` are not emitted, because no tk write path produces
  them yet. `task.pr` is added by 11-04 in `derive.ts`.
- Emission point: a decorator around the `StorageAdapter`. Every production write goes through
  `adapter.withinTransaction` of an adapter returned by `openStorage` (`packages/workspace/src/storage.ts`). There are
  exactly two production openers. `openSurfaceStore` (`packages/surface/src/store.ts`) is used by the web, the TUI, the
  daemon, the pi extension, the review component and `tk worktree clean`. The CLI main path is
  `packages/cli/src/tk.ts` (`openStorage(tasksDir, …, { readonly })` → `new CommandService(storage.adapter, …)`). The
  decorator derives events by diffing the before/after state of each touched issue, so no individual operation has to
  remember to emit. That is how "every mutation appends" holds by construction.
- Single host for v1. The spec lists cross-host log sync as an open question. Postgres-backed workspaces log only this
  host's writes. Retention/trimming stays open and is not planned.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user-authored text → events.jsonl | comment bodies, titles and review card bodies are copied into the log verbatim |
| concurrent local processes → one log file | CLI, web, TUI, daemon and pi all append |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-10 | Tampering | appendEvents seq assignment | medium | mitigate | mkdir lock + in-process chain; seq read under the lock; concurrency test pins 1..100 with two processes |
| T-10-11 | Denial of service | recorder on a committed write | medium | mitigate | append errors are swallowed after commit; a log problem never fails or rolls back a user's write |
| T-10-12 | Tampering | log line injection via comment text | low | mitigate | every line is `JSON.stringify` of an object, so newlines in bodies are escaped and cannot forge a second line; readers skip unparsable lines |
| T-10-13 | Information disclosure | events.jsonl contents | low | accept | same `.tasks/` directory and permissions as the record it mirrors; no new exposure |
| T-10-14 | Denial of service | stale lock | low | mitigate | 10s stale takeover + 5s acquire deadline (append then skipped, write still committed) |
</threat_model>
