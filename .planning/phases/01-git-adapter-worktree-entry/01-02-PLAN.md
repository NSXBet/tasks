# Plan 01-02: `tk work <id>` — worktree entry + recorded evidence

Phase 1 · Git Adapter & Worktree Entry · tracer slice completion (GIT-02's second consumer + GIT-03)

## Context

Plan 01-01 delivered `packages/git` (adapter + `resolveWorktreePath`) and wired `tk worktree create`. This plan adds the actual work-entry command from the design contract (`.agents/plans/2026-10-08-task-to-review.md`, §1 and §3):

> `tk work <id>` … Worktree path and branch derived from the issue (`tk-<id>/` naming via the resolver's `<repoName>-<id>` default, branch `tk/<id>`). It records the branch on the issue via the existing update path (`issue.branch`) and the path in issue metadata (`worktree` key). The base SHA is pinned once at `tk work` creation (merge-base vs `gitDefaultBranch`) into `metadata["changeset"].base`. `tk show` grows a WORKTREE line next to the existing BRANCH line.

Existing seams: `service.mutate` patch fields (`packages/cli/src/tk.ts:418` — `branch` already updatable), command dispatch (`tk.ts` around line 1080), help text blocks (`tk.ts:631–763`), presentation (`packages/cli/src/presentation.ts` — BRANCH line region), the workspace temp-dir test fixtures (`packages/cli/test/tk.test.ts`). Config override precedence: per-task metadata override > `worktree.dir` > default sibling — the resolver already implements it (01-01).

<action>
1. Add the `work <id>` subcommand to the tk service, dispatched like `hunk` (value + human pair, `tk.ts` dispatch chain around line 1081). Behavior, in order:
   a. Load the issue (`get(uow, id)` — unknown id fails with the existing `issue not found` shape).
   b. Determine the repo root: `gitToplevel(start)` when inside a git repo; fail with a clear message when not (`tk work requires a git repository`). Use `mainWorktreeRoot` so running `tk work` from inside an existing linked worktree targets the main checkout, matching `tk hunk`'s behavior.
   c. Resolve the target path: `resolveWorktreePath(mainRoot, `${basename(mainRoot)}-${issue.id}`, { dir: workspaceConfig?.worktree?.dir, override: issue.metadata["worktree_dir"] })` — per-task metadata override first, then `worktree.dir`, then the default sibling naming `<repoName>-<id>` (GIT-02's one-resolver rule; name construction matches the design contract).
   d. Branch name: `tk/<issue.id>`. If the branch already exists locally, do not recreate it — reuse (find the existing worktree via the adapter's `gitWorktreeList`; if none has the branch, `gitWorktreeAdd` with that existing branch; if one does, that is the re-entry path).
   e. If no worktree exists at the resolved path: create the branch `tk/<id>` (adapter: `git branch tk/<id>` from the current HEAD — add `gitCreateBranch` to `packages/git/src/commands.ts` as an enumerated command) and `gitWorktreeAdd(path, branch)`; if git fails (e.g. 'already exists' race, branch collision), `fail()` with git's stderr verbatim — never mask.
   f. Record on the issue in one transaction: `branch: "tk/<id>"` (the existing patch path), `metadata["worktree"]` = the resolved absolute path actually used, `metadata["changeset"]` = `{ ...(existing changeset metadata ?? {}), base: <merge-base of branch vs gitDefaultBranch computed via the adapter> }`. Only values read from runner results (paths the git ops accepted, SHAs from `gitMergeBase` output) are recorded — prohibition 1. If `gitDefaultBranch` returns null, `base` is not written and the human output notes why (no origin/HEAD, no main/master) — the record still carries branch + worktree path.
   g. Human output: `worktree ready at <path> (branch tk/<id>)`; `--json`: `{ id, path, branch, base, created: boolean }`.
2. Idempotent re-entry (must_have 9): when a worktree at the resolved path (or with the branch) already exists, skip creation, recompute/verify nothing about the changeset except keeping the recorded fields consistent (re-record `metadata["worktree"]`/`branch` from the discovered worktree entry if they drifted — e.g. after a config change — but never rewrite an existing non-null `metadata["changeset"].base`).
3. Help text: add `work <id>  Create/enter the task's worktree on branch tk/<id>` to the command summary and detailed usage blocks (`tk.ts` help regions mirroring `worktree create` entries).
4. Tests (`packages/cli/test/work.test.ts`, vitest imports, temp-dir git fixtures per `packages/cli/test/tk.test.ts` conventions — init a real scratch repo with an initial commit so merge-base/branches resolve):
   - happy path: `tk create` → `tk work <id>` → assert `git worktree list` (via the adapter) shows the worktree at `<parent>/<repoName>-<id>` with branch `tk/<id>`; assert the stored issue has `branch === "tk/<id>"`, `metadata["worktree"] === path`, `metadata["changeset"].base` equals a manually computed `git merge-base` in the fixture.
   - `worktree.dir` configured → path is `<dir>/<repoName>-<id>`; `metadata["worktree_dir"]` override → that exact resolved path wins over `worktree.dir`.
   - re-entry: second `tk work <id>` exits 0, reports the same path/branch, creates no duplicate worktree, and does not clobber a pre-set `metadata["changeset"].base`.
   - failure surfaces: unknown id fails; non-git dir fails with the repository message; pre-existing foreign branch named `tk/<id>` checked out in another worktree → re-entry targets it, output says so.

## Threat model

<threat_model>
ASVS level: 1 · Blocking threshold: high

- **[high] Argument/shell injection** — `tk/<id>` branch names and resolved paths flow into adapter commands. Mitigation: enumerated argv-array commands through the 01-01 adapter, no shell strings; ids validated against tk's issue-id shape before use. Blocking: any `sh -c`/shell-string git invocation in the `work` path blocks the plan.
- **[high] Path traversal via per-task metadata override (`metadata["worktree_dir"]`)** — metadata is writable via `tk update --metadata`. Mitigation: the override is resolved to a normalized absolute path by `resolveWorktreePath` (documented precedence), and it is operator-supplied local config in a single-user, local-first tool (no remote write surface at this phase); the resolver never returns a relative or non-normalized path. Blocking: an unresolved (`..`-leaving, non-normalized) override result blocks the plan.
- **[medium] Evidence spoofing** — recorded branch/path/base must originate from runner results only (Task 1 step 1f); agent-supplied file/commit lists are prohibited outright (prohibition 1). Not blocking at L1, but asserted by tests.
- **[info] Secrets** — no credentials handled; `.tasks/config.json` redaction invariant untouched.
</threat_model>
